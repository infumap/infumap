## redox_users 0.4.6

**Evidence and behavior.** Both manifests and `src/lib.rs` in full: error/locking
and file-reset helpers (159-195), authentication/zeroization (223-306), builders
and user/group parsers/formatters, ID syscall wrappers, Config/root handling,

(1049-1210,1247-1330). CI YAML invokes upstream Cargo/redoxer builds/tests only;
fixture operations use `tests/etc/`. None was executed.

Infumap -> dirs 5.0.1 -> dirs-sys 0.4.1 selects this dependency only on Redox,
with **no auth/default feature**. `dirs-sys/src/lib.rs::target_redox::home_dir`
gets the real UID, opens the basic passwd database and returns that user's home.
Libredox provides the explicit ID calls; its separately recorded review remains
in place. Basic construction reads `/etc/passwd`, shared-locked on Redox. Group
construction reads `/etc/group`; only the explicit authenticator reads shadow.
Config permits a caller-selected filesystem root and enables writes explicitly.
Save truncates/rewrites those same opened account files, rather than unrelated
paths; there is no implicit save on drop. Login/shell methods construct and
return a Command with the requested UID/GID/home/environment; they do not spawn
it. Optional authentication uses declared getrandom/Argon2/zeroize and the
configured delay on failure. Those costs and sensitive file accesses implement
the documented account-management purpose; there is no upload or hidden execution.

**Nonblocking observations.** `is_safe_string:193-195` rejects semicolons but
allows newlines in directly mutable name/home/shell fields; group serialization
at 682-702 also inserts public `password` without validation. Untrusted fields
can therefore corrupt/inject database structure when a privileged caller
explicitly saves them. This is account-database input hardening, inactive in
Infumap's basic read-only path; no attacker-controlled privileged save path was
established. `auth::Full::verify:286-294` panics on invalid encoded hashes despite
the broader unset-hash documentation at 396-400; only the exact `!` sentinel is
handled. Malformed password databases can cause authentication availability
failure, with auth disabled in this consumer. These are observations, not fixes
or established safe-to-run violations. Saves are nontransactional; crash/error
recovery and authentication protocol/cryptographic correctness were not proven.

**Decision and limits.** No concerning changes found within the reviewed scope;

## aligned-vec 0.6.4

**Evidence and behavior.** Both manifests; all `src/lib.rs:1-1419` and
`src/raw.rs:1-415`, including alignment traits/constants, AVec/ABox ownership,
allocation/reserve/shrink/drop, raw conversions, sequence operations, macros,
Send/Sync and optional serde. The sealed alignments check power-of-two values;
raw allocation/growth checks products and routes through alloc/realloc/dealloc.
Memory work follows caller-selected capacity, elements and alignment. The serde
visitor caps initial preallocation to 1 MiB, not total sequence memory. Generic
clone/drop/serialization behavior is the caller's element/serializer behavior.
There is no filesystem, environment, network, process or worker path.

Infumap -> image -> ravif -> rav1e 0.8.1 and v_frame 0.3.9 use aligned storage
for SIMD pixels/coefficients, with default/std enabled and **serde disabled**.
V_frame `plane.rs:101-147` constructs ABox pixel slices using exact repeat/take
iterators or from_slice, then into_boxed_slice; these already have capacity equal
to length. Pixel bounds (`pixel.rs`) imply Copy integer types. Rav1e
`predict.rs:427-458` constructs a fixed nonempty i16 compound prediction buffer.
These examined callers neither invoke AVec::extend_from_slice nor directly use
the hidden raw-copy helper. Separate equator assertions are reviewed below.

**Nonblocking memory-safety findings (source-derived; not executed).**

1. `lib.rs:801-809::AVec::extend_from_slice` is available for **T: Clone**, but
   bit-copies supplied elements without clone. With String or another owning
   non-Copy value, the source and destination own the same allocation; dropping
   one leaves the other dangling and dropping both can double-free. This is a
   concrete safe-API soundness defect. The inspected pixel/coefficients paths
   use Copy types and do not call this method; no affected Infumap path was found.
2. `raw.rs:254-275::ARawVec::shrink_to` calls realloc with `len * size_of::<T>()`
   and stores the result with NonNull::new_unchecked without checking it.
   Shrinking a previously allocated empty non-ZST vector via
   `lib.rs:540-552::shrink_to/shrink_to_fit` requests a zero-size realloc, violating
   the allocator API's precondition. A nonzero shrink returning null similarly
   violates NonNull's precondition instead of handling allocation failure.
   Into_boxed_slice at 583-589 inherits shrink behavior. The exact-capacity
   construction paths above skip reallocation, including zero-length
   construction with zero capacity. This is not a proof of all downstream paths.
3. `lib.rs:748-755::__copy_from_ptr` is a public safe function that reads an
   arbitrary pointer/length without enforcing validity or ownership. Its comment
   warns against user calls, but the signature cannot enforce that. Calling it
   directly with an invalid pointer can cause invalid reads; copying owning
   values can duplicate ownership. The public avec macros supply a live
   ManuallyDrop array and transfer it, so that normal macro path differs from
   direct misuse. No direct Infumap/inspected consumer call was found.

These defects are relevant to a separate soundness/production-input hardening
review. No concrete path to unexpected harmful machine behavior under this
batch's operator-vetted-input/actual consumer scope was established. Per policy,
they are preserved without withholding an otherwise completed safe-to-run
review. They have not been fixed or disproved; no safe-to-deploy acceptance is
claimed, and no production attacker path was investigated sufficiently to record
a confirmed safe-to-deploy violation.

**Decision and limits.** Certified safe-to-run; nonblocking observations. Full
exact-version AI source/effects review, without a comprehensive unsafe-code,
allocator, panic, iterator-contract or adversarial-input proof. Record:
`infumap/supply-chain/audits.toml`, `[[audits.aligned-vec]]`.
