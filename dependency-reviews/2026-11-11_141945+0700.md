## wasm-streams 0.4.2

**Evidence and behavior.** Both manifests, `.cargo/config.toml`, all 21 Rust
source modules under `src/` (readable/default/BYOB readers, Rust stream and
AsyncRead adapters, underlying sources, writable/sink/AsyncWrite adapters,
transform, queuing strategy, JS declarations and conversion helpers), plus the
fetch example and test I/O entry points. Reqwest 0.12.28 selects this dependency
only on wasm32 with its stream feature. `reqwest/src/wasm/response.rs:145`
wraps the response body with `ReadableStream::from_raw(...).into_stream()`.

Stream constructors wrap caller-supplied Rust or JS objects. Polling forwards
chunks through those objects and promises; writer readiness supplies backpressure.
The underlying reader closes/discards on EOF/errors and aborts pending pulls on
drop. Owned reader adapters cancel their supplied stream on drop; borrowed reader
adapters release the lock. `Closure::forget` in the cancellation catch handlers
hands lifetime management to JS, rather than starting an unrelated worker.
FFI declarations bind Web Streams constructors/methods, with no eval, embedded
code download or start hook. The example and fetch test request the fixed public
wasm-ferris PNG from rustwasm.github.io and log/read response chunks; these do
not run during a consumer build. Packaged Cargo config selects wasm32 for
standalone development, not Infumap's compilation target.

**Nonblocking observation.** `readable/into_async_read.rs:75–123` retains an
in-flight JS read sized for an earlier poll. If a later poll supplies a shorter
destination and the earlier read completes with more bytes, the slice at line 121
panics (the length assertion is debug-only). This is a source-derived availability
defect, not a reproduced result; bounds checking prevents a silent buffer overwrite.
Reqwest's inspected caller uses IntoStream, not this BYOB AsyncRead adapter.

**Decision and limits.** Full exact-version AI source review supports safe-to-run
certification, with the observation retained. JS objects and caller stream/sink
implementations may execute their own callbacks or perform expected I/O; this
does not certify them or the wasm-bindgen implementation. No comprehensive JS
reentrancy, cancellation or resource-limit proof is claimed.

## schannel 0.1.30

**Evidence and behavior.** Both manifests; all production source modules:
`lib`, `cert_store`, `cert_context`, `cert_chain`, `ctl_context`, `crypt_prov`,
`crypt_key`, `ncrypt_key`, `key_handle`, `schannel_cred`, `security_context`,
`context_buffer`, `alpn_list`, `tls_stream`; security-relevant test paths and
archive member inventory. Windows-only through rustls-native-certs 0.8.5.
Its `src/windows.rs::load_native_certs` opens the current-user ROOT store,
enumerates certificates, checks enhanced usages/time validity and returns public
DER bytes. It does not acquire/export private keys, import PFX, mutate roots,
or call Schannel's TLS stream implementation.

The wider public API deliberately exposes Windows certificate/key operations:
explicit add/delete/property changes, PFX import/export including private keys,
provider/key-container acquisition and key import. PFX import can persist keys
unless no_persist_key is selected; dropping the temporary store is not key
deletion. This is expected credential-management functionality on caller-selected
objects, not a background credential search or upload. TLS operates on the
supplied Read+Write transport; credentials disable default credentials and use
supplied certs. Runtime symbol lookup resolves RtlGetVersion from already-loaded
ntdll.dll to choose the OS-supported credential structure; no arbitrary library
path or downloaded code is involved. Chain validation delegates to Windows;
cache-only revocation does not promise offline AIA/root retrieval. Such OS
certificate retrieval implements chain validation, not an unrelated endpoint.
See [Microsoft's PFX persistence contract](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-pfximportcertstore)
and [chain retrieval flags](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certgetcertificatechain).

**Nonblocking observations.** `src/test.rs:434–565` acquires/creates the
machine keyset named `schannel-rs test suite`, generates an exportable signing key,
and installs a one-day localhost certificate into ROOT. `local_root_store:569–574`
chooses LocalMachine in CI and CurrentUser otherwise. `localhost_cert:577–641`
skips if SCHANNEL_RS_SKIP_SERVER_TESTS exists; otherwise it prints a warning,
deletes expired matching-friendly-name roots and installs one when needed.
Key-container cleanup is not provided there. Reconstructing/running these
upstream tests could change machine trust and leave keys behind; this is not
described as harmless. However, lib.rs:70 gates them behind cfg(test), and the
published archive omits the entire `test/` fixture directory referenced by
include_bytes!/include_str! in multiple modules. The Windows unit-test suite
cannot compile as published; on non-Windows the whole crate is cfg-excluded.
No executable path to this mutation exists in the reviewed consumer or the
unmodified archive's test suite. This is therefore recorded as a latent,
nonblocking test-only concern, not a confirmed criterion violation. No fixtures
were supplied, no guard was changed and no such tests were executed.

`tls_stream.rs:778–790::write_out` also retries indefinitely if the supplied
writer returns Ok(0) with pending output, rather than returning WriteZero.
That can consume CPU with a zero-progress generic transport. The graph's
rustls-native-certs path does not instantiate this TLS implementation.

**Decision and limits.** Full exact-version AI source review supports safe-to-run
certification with the above limitations. No comprehensive Windows FFI ownership,
TLS validation, ALPN layout or hostile-peer audit is claimed. Windows/native
cryptography was inspected, not executed. This is not approval to install a
test certificate or to run a reconstructed upstream test suite.

## hashlink 0.8.4

**Evidence and behavior.** Both manifests and all five source modules:
`lib`, `linked_hash_map`, `linked_hash_set`, `lru_cache`, optional `serde`.
Yaml-rust2 0.8.1 uses LinkedHashMap<Yaml,Yaml>; no optional features are enabled.
The map stores hashbrown table entries pointing into owned, linked heap nodes.
Insertion/removal/reordering manages those nodes and a reusable free list;
clear/drop/drain free or recycle owned entries. Set operations delegate to the
map. LruCache evicts map entries according to caller capacity/access.
Serde serializes/deserializes caller values through supplied serializers,
including their size hints; it chooses no external storage. There is no OS I/O,
environment access, subprocess, payload, background execution or build hook.

**Nonblocking observation.** `linked_hash_map.rs:1424–1429` implements Send for
shared Iter using K:Send,V:Send, although next at 1527–1540 yields &K and &V.
For example, Send but non-Sync Cell values can thereby be shared across threads
through a scoped iterator while the original thread retains shared access,
allowing unsynchronized mutation/data races. Shared RawEntryBuilder:969–975
has the same missing Sync distinction for shared references. Mutable IterMut
also yields shared keys, so its key bound needs the same consideration.
This is a concrete generic thread-soundness concern, not a reproduced exploit.
[Rust's Sync contract](https://doc.rust-lang.org/std/marker/trait.Sync.html)
explains the required relationship between shared references and Send.
Yaml's variants contain strings, numbers, vectors and recursively these maps;
the inspected consumer does not instantiate them with Cell/non-Sync payloads.
No affected consumer path or unexpected machine side effect was established.

**Decision and limits.** Full exact-version AI source review supports safe-to-run
certification with this nonblocking observation. It does not certify arbitrary
generic/concurrent use, every raw-pointer/list invariant, panic safety or
hashbrown itself. Memory use follows caller entries/capacities; raw entry APIs
and custom hash/equality/drop/serializer implementations retain their contracts.

## ordered-multimap 0.7.3

**Evidence and behavior.** Both manifests, `.cargo/config.toml`, module routing,
the complete production `src/list_ordered_multimap.rs:1–3539`, optional serde
implementation and packaged CI/release configuration. Rust-ini 0.20.0/0.21.3
uses it for property/section storage with `default,std`; serde is not selected.
The multimap combines dlv-list VecLists for keys/values with a hashbrown index,
maintaining per-key head/tail and insertion order. Append, replace, remove,
pop, packing, draining and iteration operate on those in-memory containers.
Mutable iterators use raw pointers to return caller-owned value references;
no pointer is used for hardware/native execution or an external storage target.
std uses RandomState; no_std requires an explicit hasher rather than obtaining
one from a hidden service. Serde consumes/emits sequences through supplied
implementations. Cargo config adds warnings; CI publishing uses the upstream
CARGO_API_KEY and coverage goes to Codecov, neither wired into consumer builds.

**Nonblocking observations.** `retain_helper:1549–1607` defers neighbor-link
updates until after removing values. Removing adjacent values of one key queues
updates targeting an already removed node; `values.get_mut(index).unwrap()`
at 1597 can panic, and retained bookkeeping can remain inconsistent. This is a
source-derived availability/in-memory integrity defect; neither rust-ini source
calls retain in the inspected versions. No reproduction or fix was performed.
`KeyValuesMut` has shared key references (`3217,3220`) yet its Send implementation
at 3304–3309 requires Key:Send rather than Key:Sync. Generic Send/non-Sync keys
can therefore cross threads through shared references; rust-ini uses String
keys/values (or its string case wrapper) and does not trigger this condition.
The same Rust Sync contract cited above applies. No unrelated data mutation or
exfiltration path was found.

**Decision and limits.** Full exact-version AI source review supports safe-to-run
certification with the observations retained. No full iterator-aliasing,
list/index/panic-safety or hostile-configuration proof is claimed. Dlv-list,
hashbrown and their transitive build dependencies remain separate obligations.
