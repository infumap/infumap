## Advisory findings in the packaged `multiversion` benchmark graph

The added `multiversion` 0.8.1 `Cargo.lock` contains `crossbeam-epoch` 0.9.18 through the `criterion` dev-dependency, via `rayon`, `rayon-core` and `crossbeam-deque`. RustSec reports invalid pointer dereferences when affected `Atomic` or `Shared` pointer-formatting implementations encounter an invalid underlying pointer. The lockfile also contains `atty` 0.2.14 through Criterion and Clap. RustSec reports a potentially unaligned read on Windows, which in practice requires an allocator that can return insufficiently aligned pointers, and lists `atty` as unmaintained. I confirmed the affected versions with `cargo audit --no-fetch --no-yanked --file <archive>/Cargo.lock`. Reachability of either trigger in the upstream benchmark was unverified. [RUSTSEC-2026-0204](https://rustsec.org/advisories/RUSTSEC-2026-0204), [RUSTSEC-2021-0145](https://rustsec.org/advisories/RUSTSEC-2021-0145), [RUSTSEC-2024-0375](https://rustsec.org/advisories/RUSTSEC-2024-0375)

Cargo uses Infumap's lockfile for the consumer build and excludes dependency dev-dependencies. Infumap locks `crossbeam-epoch` 0.9.21 and has no `atty` entry. InfuSDK has neither package. These findings affect use of the upstream standalone lockfile and establish no `safe-to-run` violation by the reviewed delta in either project store. The standalone advisory scan skipped yank checks after the cached index lacked several benchmark crates.

## `futures-core` 0.3.34 → 0.3.32

InfuSDK uses `futures-util` directly, including `BoxFuture` in `src/web/listener.rs`. `futures-core` also enters its graph through `futures-channel`, `http-body-util`, and `hyper`. This is a reverse delta to the InfuSDK lockfile version.

The package version changes in `Cargo.toml` and `Cargo.toml.orig`, and `.cargo_vcs_info.json` changes the commit SHA. The packaged `Cargo.lock` rolls the optional `portable-atomic` resolution back from 1.13.1 to 1.11.1. The manifest keeps the same `1.3` requirement with `require-cas`, `optional = true`, and `default-features = false`. InfuSDK's lockfile has no `portable-atomic` entry. `src/lib.rs`, the `std`/`alloc` feature definitions, the bare-metal cfg in `src/task/__internal/mod.rs`, and the atomic backend selection and unsafe waker operations in `atomic_waker.rs` are byte-identical. The artifact has no build script and the delta introduces no execution, I/O, or resource behavior in the consumer graph.

Fresh base evidence is Google's 0.3.28 audit, bytecode-alliance's 0.3.28 → 0.3.31 audit, and Mozilla's 0.3.31 → 0.3.34 audit. The AI review covers the reverse delta and excludes a full source audit of the base or its dependencies. No concerning changes found within the reviewed scope. The delta qualifies for `safe-to-run` in `infusdk/supply-chain/audits.toml`.

## `futures-macro` 0.3.34 → 0.3.32

InfuSDK's direct `futures-util` dependency uses its default async macro feature and selects `futures-macro` at the same 0.3.32 release. This is a reverse delta to the InfuSDK lockfile version.

Both manifests change the package version and change the `syn` requirement from `3.0` to `2.0.52`, keeping `full`. `proc-macro2` and `quote` requirements and features remain identical. `.cargo_vcs_info.json` updates the release commit SHA. The packaged `Cargo.lock` also changes its standalone resolutions for `syn`, `proc-macro2`, `quote`, and `unicode-ident`. The actual InfuSDK graph uses `syn` 2.0.117, shared with other macro consumers. Infumap's 0.3.34 macro uses `syn` 3.0.9. Both contextual `syn` archives match the registry index and respective project locks. Both manifests have `build = false` and use the parsing/printing library with its normal macro-related dependencies. This review did not audit the full `syn` sources.

The crate still executes as a procedural macro at build time with the same entry points and source in `src/lib.rs`, `join.rs`, `select.rs`, `stream_select.rs`, and `executor.rs`. Those functions parse Rust expressions, patterns and items with `syn`, then emit polling, pinning, stream selection, or test-wrapper tokens. Existing unsafe pinning in `join::bind_futures` and `select::select_inner` is byte-identical. The manifest adds no build hook or extra feature to either parser line. The major-version selection changes the parser compiled for macro expansion. Cargo-vet assesses that dependency separately, and `syn` did not appear among the InfuSDK gaps in the live pre-certification check.

Fresh base evidence is bytecode-alliance's 0.3.31 full audit and 0.3.31 → 0.3.34 audit. The AI review covers the reverse delta and excludes a full review of either release or a claim about identical parser behavior across `syn` majors. No concerning changes found within the reviewed scope. The delta qualifies for `safe-to-run` in `infusdk/supply-chain/audits.toml`.

## `multiversion` 0.8.0 → 0.8.1

Infumap's `image` 0.25.10 enables EXR via its default formats. `exr` 1.74.3 uses `multiversion` on x86/x86_64 to dispatch the forward and inverse 8×8 DCT batch routines to AVX2 or the baseline implementation (`src/compression/dwa/discrete_cosine_transform/mod.rs`, `dct_forward_8x8_batch` and `dct_inverse_8x8_batch`).

`Cargo.toml` and `Cargo.toml.orig` change the package version and raise the minimum `multiversion-macros` version from 0.8.0 to 0.8.1. The normalized manifest adds `autolib = false` while retaining the explicit `src/lib.rs` target and moves the same `std` default and forwarding feature. The crate still declares `build = false`. `.cargo_vcs_info.json` changes the release SHA. The added v4 `Cargo.lock` describes the standalone package, its library dependencies, and existing development and benchmark dependencies. Inspection of the whole file found only the local root and crates.io entries. The benchmark advisory findings are above. `src/lib.rs`, the explicit test targets and the benchmark source are byte-identical. The consumer manifest still selects the same `target-features` requirement and forwards `std` to the macro crate.

For dependency context I compared the crates.io `multiversion-macros` 0.8.0 and 0.8.1 archives, SHA-256 `b093064383341eb3271f42e381cb8f10a01459478446953953c75d24bd339fc0` and `a05e0c3c3e4edaa21d87c645852ed0b0c3663752bcc6ec43353bd6189dce35e1`. Both match the index and the latter matches Infumap's lockfile. The macro source, including `src/lib.rs::multiversion`, `src/dispatcher.rs::static_dispatcher_fn` and `src/target.rs::features_detected`, is byte-identical. The normalized macro manifest retains the same explicit proc-macro target, dependencies and features with no build script. The packaged macro lockfile is new and has the same library dependencies as the macro manifest. The wrapper delta therefore changes the minimum version of a compile-time dependency without introducing changed expansion code between those two macro artifacts. The architecture cfgs, CPU detection, unsafe target calls and runtime dispatch code are unchanged. The macro crate remains an independent cargo-vet gap.

Fresh base evidence is Mozilla's full audit for 0.8.0. The AI review covers the wrapper delta in the consumer graph. It excludes an independent certification of the macro crate or the standalone benchmark graph. No concerning changes found within the reviewed scope. The delta qualifies for `safe-to-run` in `infumap/supply-chain/audits.toml`.
