## multiversion-macros 0.8.1

**Evidence and behavior.** Both manifests and all seven modules:
`src/{lib,cfg,dispatcher,match_target,multiversion,target,util}.rs`.
`multiversion 0.8.1` reexports these macros; EXR uses them on its x86/x86_64
DCT functions (`exr/src/compression/dwa/discrete_cosine_transform/mod.rs:177,190`).
The enabled feature is `std`. Attribute parsing selects supplied architectures,
CPU/features and dispatcher style. Expansion clones the caller's function body,
adds cfg/target_feature attributes, normalizes arguments and emits target helpers.
Static dispatch uses compile-time feature checks; direct dispatch caches a CPU
feature index; indirect dispatch caches a pointer to the resolver or a generated
function. Pointer transmutation in `Dispatcher::indirect_dispatcher_fn` only
reconstructs those generated function pointers. Runtime CPU detection precedes
specialized calls; no downloaded executable, external process or hidden payload
is selected. No filesystem, credential, environment scan or networking operation
exists in the macro implementation or generated dispatcher.

Focused dependency context inspected target-features 0.1.6's architecture/CPU
lookup and feature iteration, plus its build script. The latter reads packaged
feature/CPU text and Cargo target variables and writes generated tables/docs
under OUT_DIR. That separate crate's tables and full implementation are not
new certifications here. The macro's code generation and atomics are expected
CPU dispatch, not unrelated work; resources scale with supplied syntax/targets.

**Nonblocking observation.** `src/target.rs::Target::features_detected` matches
`"risv64"` instead of `"riscv64"`, leaving a supplied `riscv64` target to form
`is_riscv64_feature_detected!` instead of the intended `is_riscv_feature_detected!`.
This can fail compilation when the runtime dispatch branch is emitted. EXR's
observed invocations select only x86 targets. This is an unexecuted source finding,
not a path to unexpected harmful machine behavior; no fix or compiler reproduction
was attempted. No complete proof of dispatcher ABI/lifetime soundness is claimed.

**Decision.** No concerning changes found within the reviewed scope; certified
safe-to-run for this full version, with the nonblocking observation retained.

## y4m 0.8.0

**Evidence and behavior.** Both manifests; complete `src/lib.rs`, README,
resize example, `.travis.yml` and `scripts/travis-doc-upload.cfg`; inventory
includes an encrypted historical CI key at `scripts/id_rsa.enc`. Av-scenechange
requires it and exposes a Y4m decoder route. The library reads only its supplied
Read stream and writes only its supplied Write stream. Headers are bounded to
1024 bytes; frame storage follows parsed width/height/colorspace and the
configured Limits (default 1 GiB). Frame::from_u16 reinterprets supplied sample
slices as byte views; there is no foreign code execution. Encoder validates
plane lengths and emits header/frame bytes to its provided writer. No path
from metadata to filesystem selection, credentials or subprocess execution exists.
Resize is a dev-only dependency, and the example opens only specified CLI
input/output paths or stdin/stdout.

**Nonblocking observations.** `src/lib.rs:295–300` computes plane sizes using
unchecked usize multiplication/addition, and `:408–413` adds plane sizes before
checking the byte limit. Oversized/malformed dimensions can panic with overflow
checks or wrap without them, invalidating the represented sizing/limit reasoning
and potentially causing later slicing panics. No unsafe out-of-bounds effect is
established by this finding. This remains an unfixed parser/resource-hardening
defect; operator-vetted inputs and the absence of unrelated machine effects make
it nonblocking for safe-to-run. No hostile-input resistance claim is made.

`.travis.yml:16` downloads an upstream documentation-upload shell script over
HTTP and pipes it to sh after CI success. Running that standalone upstream CI
configuration risks executing substituted code. Cargo does not execute Travis
hooks when building/using this dependency, and there is no build.rs or source
reference to the encrypted key or uploader config. This is a dormant upstream
CI supply-chain weakness, not behavior on Infumap's build/run machine. The
remote script was neither fetched nor executed; encrypted key contents were
not decrypted, and no claim about their validity is made.

**Decision.** No concerning changes found within the reviewed scope; certified
safe-to-run, full version, with both nonblocking observations retained. Native
sample-byte representation and comprehensive arithmetic/format correctness were
not proved. No finding was fixed or disproved.
